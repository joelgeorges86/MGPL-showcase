# Catalogue sources: licences, attribution and links

_Added by WU-009a (#158, task proposal 017); comparison rules revised by WU-009a2 (task proposal 018); Steam moved to the Steam Web API, and cross-catalogue IDs added, by WU-009a3 (task proposal 022, carrying out proposal 020). This file is written before any of the data it describes is stored (#158 acceptance criterion "Licence notes")._

Every fact the catalogue stores keeps a link to the exact source version it came from. A value without such a link is marked `generated` and is never shown as fact (task proposal 017, accuracy rule 2).

## Wikidata: the backbone

|                          |                                                                                                                                                                                                                                                                |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **What**                 | Title (English label, or the `mul` label for all languages), release dates with precision, platforms, developers, publishers, series, genres, Steam app ID (P1733), English Wikipedia article, for every item that is an instance of video game (P31 = Q7889). |
| **Licence**              | Structured data is released under **CC0 1.0** (public domain dedication). No attribution is legally required; MGPL gives it anyway, as a link per fact.                                                                                                        |
| **Access**               | `https://query.wikidata.org/sparql`, POST, one request at a time (`scripts/catalogue/wikidata-ingest.mjs`). The User-Agent names MGPL and a contact, as the Wikimedia User-Agent policy requires; `CATALOGUE_CONTACT` overrides the contact.                   |
| **Link stored per fact** | `https://www.wikidata.org/w/index.php?title=<QID>&oldid=<revision>`: the revision read. The current page is `https://www.wikidata.org/wiki/<QID>`.                                                                                                             |

## Steam Web API: the cross-check

|                          |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **What**                 | For titles Wikidata links to a Steam app ID: name, type (game, DLC), free-to-play flag, developers, publishers, franchises, Steam's release date and, where Steam records one, the original release date; platforms (Windows, macOS, Linux) and the Steam Deck compatibility category; the store's player, feature and controller category IDs; supported languages with audio and subtitle flags; content descriptor IDs; the review summary (count and percent positive). For DLC, the base game (`parent_appid`).                                                                |
| **Not kept**             | Price (prices come from ITAD), descriptions, images, screenshots, videos, review text, tags and any link other than the store page. They are not requested, and anything returned anyway is dropped.                                                                                                                                                                                                                                                                                                                                                                                |
| **Terms**                | The Steam Web API Terms of Use, with the project's existing key (`STEAM_API_KEY`, one per account, shared with the app's library sync). Facts only. The store's `appdetails` route is not used for bulk fetches (proposal 020: the Steam Subscriber Agreement §2.G and §4.C). The app's on-demand system-requirements lookup (`src/services/steamSpecs.ts`) is unchanged.                                                                                                                                                                                                           |
| **Access**               | `https://api.steampowered.com`: `IStoreBrowseService/GetItems/v1` (100 app IDs per call), `IStoreService/GetAppList/v1` (the DLC list, paged) and `IStoreBrowseService/GetStoreCategories/v1` (`scripts/catalogue/steam-ingest.mjs`). One request every 1.5 s by default, never faster than one a second. **The first network error, non-200 status, non-JSON body or malformed response stops the run, with no retry**; every step is resumable. A DLC list page is checked whole before any of it is written. A listed app with no type is kept as not usable and never compared. |
| **The key**              | Read from `STEAM_API_KEY`, supplied by `doppler run --`. It is sent only as the request's `key` parameter. It is never printed, logged or written to a file, and no message includes a request URL. Error messages also mask any key value or `key=` parameter. A network error is named only by a known error code, never by the exception's own text. Agents do not run the keyed steps: the Principal Operator does.                                                                                                                                                             |
| **Link stored per fact** | `https://store.steampowered.com/app/<appid>/`, with the fetch time and the route.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## Generated drafts (the fill stage, S3)

`scripts/catalogue/enrich-gemini.mjs` (WU-029, task proposal 029) asks Gemini 3.1 Flash-Lite, through the AGENTS.md section 3.1 run guard, for three kinds of draft. Each is labelled `generated` and is never shown as fact:

- **descriptions:** original text of 40 to 70 words. One that shares 8 or more consecutive words with the Wikipedia lead it was given is not kept (`rejected`), to keep the article's CC BY-SA wording out of what is stored;
- **session-friction drafts:** the `AppGameFriction` fields Steam does not state. The Steam categories in the table above are copied beside them as `sourced`: a listed category is `true`, an unlisted one `null`, since not listed is not evidence of no;
- **genre flags:** the 11 `AppGames` flags and a primary genre, only for games the rule mapping from Wikidata genre labels (`GENRE_RULES`) places in no flag.

A game whose description was rejected, or that the model found too thin with Wikipedia context, can be drafted again without it: `--context none --fill-from wikipedia` takes only those games (WU-030).

The model is given only `agree` and `single` values; `conflict` fields are left out. Each record keeps the Wikidata revision link, the Steam app link and, if one was used, the Wikipedia revision link, with the model, prompt version, run and ledger attempt. The drafts are written to the output folder the ledger entry names, outside the repository, and nothing goes into the app database: promotion is a later, reviewed step.

## The sample check (WU-033a)

#158 requires 100 randomly chosen records to be checked by hand against their cited sources, with the error rate recorded, before drafts are used. Since 2026-10-13 (task proposal 033) the check gates promotion into the app, the embeddings, and the full friction and genre runs. Each kind of draft is checked separately.

`scripts/catalogue/sample-check.mjs` (no network):

- `draw --kind description --in <drafts> [--in <more drafts>] --seed <seed> --out <folder> [--titles <wikidata.jsonl>]` takes the latest record per game across the files, keeps the games whose latest record is `ok`, and picks 100 at random from the seed. The same files and seed always give the same sample. It writes a CSV sheet, an HTML page with each record's source links, and a meta file holding the seed, each input's SHA-256 and each row's game and draft hash. It never overwrites a file, and the folder must be outside the repository.
- `score --sheet <csv>` checks every row against the meta file, including that the draft in the sheet is the one drawn, counts the verdicts (`correct`, `minor`, `wrong`, `unverifiable`) and writes a summary with the error rate (`wrong` over `correct`, `minor` and `wrong`) and its 95% Wilson interval. The sheet must also be outside the repository. A spreadsheet that edits the sheet must save it as CSV UTF-8 with commas; any other save that changes a draft's text makes `score` refuse the row.

**The line** (proposal 033, decision 2): every row has a verdict, and at most 3 of the 100 are `wrong`. `unverifiable` rows are counted and reported but not limited, and they are left out of the error rate; the operator weighs them when accepting (decided 2026-10-13). Meeting the line is not acceptance. The Principal Operator accepts a sample by filling in `accepted_by` and `accepted_at` in the summary by hand; no script writes them, and `score` will not replace a summary that has them.

## Embeddings (WU-032)

`scripts/catalogue/embed-descriptions.mjs` (#199, task proposal 032) gives each game with an `ok` description one vector, for "games like X":

- **The text:** the Wikidata label, a full stop, and the latest `ok` description, using the same latest-record rule as the sample check.
- **The model:** `text-embedding-005` in `us-central1`, as `SEMANTIC_SIMILARITY` at 768 dimensions, with `autoTruncate` off. The request goes through the AGENTS.md section 3.1 run guard under its own ledger entry.
- **The output:** each vector goes to `embed-descriptions-text-embedding-005-768.jsonl` in the entry's output folder, outside the repository. It is stored as base64 of little-endian float32, with the SHA-256 of the text it embeds and the run and attempt it came from.
- **Resuming:** a game whose text has not changed is not sent again. A changed description is embedded again, and the latest record wins.
- **What a vector inherits:** it carries no fact of its own. It is derived from a `generated` description, so it is used only after that description's sample check is accepted (task proposal 033).

## Where the data lives

`data/catalogue/` on the operator's PC, which is not committed (`.gitignore`). Each file is JSON Lines, append-only and resumable:

| File                     | Written by                      | Contents                                                                                                                                                                                   |
| ------------------------ | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `wikidata-ids.jsonl`     | `wikidata-ingest.mjs list`      | every video game item and its revision, a snapshot                                                                                                                                         |
| `wikidata.jsonl`         | `wikidata-ingest.mjs details`   | one record per item, with its source links, and its release events (date, platform and place)                                                                                              |
| `companies.jsonl`        | `wikidata-ingest.mjs companies` | per developer or publisher: the names Wikidata knows it by (label, aliases, official name), with its revision link                                                                         |
| `wikidata-xids.jsonl`    | `wikidata-ingest.mjs xids`      | per item: its cross-catalogue IDs and aliases, with its revision link                                                                                                                      |
| `steam.jsonl`            | `steam-ingest.mjs` (`games`)    | one record per Steam app ID, facts only, with the route it came from                                                                                                                       |
| `steam-dlc-ids.jsonl`    | `steam-ingest.mjs dlc`          | every DLC app ID Steam lists; `steam-dlc-ids.done.json` marks a finished listing                                                                                                           |
| `steam-dlc.jsonl`        | `steam-ingest.mjs dlc`          | one record per DLC, facts only, with its base game (`parent_appid`)                                                                                                                        |
| `steam-categories.json`  | `steam-ingest.mjs categories`   | the store's category IDs, names and types                                                                                                                                                  |
| `agreement.jsonl`        | `agreement.mjs`                 | per item and field: `agree`, `partial`, `conflict`, `distinct`, `single` or `none`, with the value, the basis of any agreement and the source links; and Steam's store facts under `store` |
| `conflicts.jsonl`        | `agreement.mjs`                 | the review queue: every `conflict` and `partial` field                                                                                                                                     |
| `agreement-summary.json` | `agreement.mjs`                 | counts per field and status                                                                                                                                                                |

A field is promotable only with status `agree`, and only for the values in `value`. A `conflict` goes to review and is never resolved by a script. A `single` field needs a second source before promotion.

Comparing two values is only evidence when both describe the same thing (task proposal 018). The rules:

- **Every agreement says why.** `basis` records how the two values were matched: equal after normalising, equal after removing a Steam edition label, matched through a Wikidata company name, or a date matched to a Wikidata release event for Windows or with no platform given. An equal value alone does not prove the sources mean the same event, so the basis is kept for review.
- **Dates.** Wikidata gives release events: each release-date statement with its platform and place. Where Steam records an original release date for the app, that date is compared with any Wikidata event, since both claim to be a release of the game, and the basis names the event's platform (`steam_basis` is `original_release_date`). A Steam original date later than every Wikidata event is `distinct`; one between events that matches none is a `conflict`. Otherwise Steam gives only the date its store lists for the app, and the rest of this rule applies. They are compared only where they can describe the same release: an event for Windows, or one with no platform given, at the precision both give. A finer date from one source is kept in `single_source`. A Steam date later than every Wikidata event is `distinct`: a later store release, not a disagreement. It is not compared, promoted or queued, and the original date stays single-source. A Steam date earlier than every event, or one between events that matches none, is a `conflict`.
- **Steam's store facts** are also kept unchanged under `store`, as `steam_store_release_date` and `steam_store_publishers`, scoped to the app as listed at the fetch time. They do not claim to be the first date on Steam or the original publisher.
- **Companies** match when Steam's name equals the Wikidata label, or one of the names in `companies.jsonl` (aliases and official names, English or `mul`), of exactly one company in the list. A name that two companies carry is ambiguous: it is listed in `ambiguous` with the candidates and goes to review. Unambiguous legal designations at the end, such as ", Inc.", "Ltd", "GmbH" or "AB", are ignored, but never in a name with a bracket, and "Co" and "Company" are never ignored, since they can be part of a name (in "Studio (AG)" the "AG" stays). A Steam platform note `(Mac)`, `(macOS)` or `(Linux)` is also ignored. A Steam name that is only punctuation is kept as unmatched and sends the field to review. Any other bracketed text, such as `(UK)`, is part of the name. Every match is listed in `matches`, with the company's revision when the match came from `companies.jsonl`. A predecessor, successor or parent company is not a match.
- **Lists** (developers, publishers, platforms). If every Steam value matches a Wikidata value, the matched values `agree`, and any extra Wikidata values (a port studio, a regional publisher, another platform) stay single-source in `single_source`. If Steam names something Wikidata does not, the field is `partial` and goes to review. If nothing matches, it is a `conflict`.
- **Titles** are compared after normalising, which removes only these: whitespace, punctuation other than "#", the trademark signs ™ ® ©, and letter case, with "&" read as "and". Every other character is kept: letters, combining marks (accents, vowel signs), numbers, "+", "#" and symbols such as "$" or "∞". So "Café" and "Cafe", "Game+" and "Game", or "Game $" and "Game" differ. There is no compatibility folding, so "Game ²" and "Game 2", or a full-width title and its ASCII form, stay different. A title that is only punctuation never agrees. If they differ, Steam's edition labels are removed and they are compared again. Only these exact forms are removed: `(2007)` (any year), `(Classic)`, `(Classic, 2005)`, `Game of the Year Edition` and `GOTY Edition`. A removal that would leave no title is not made. Nothing else is removed, since "(Remastered 2020)", a "Definitive Edition" or a bare "GOTY" can be a different product.

Interrupted runs: if a run stops mid-write, the next run drops the one incomplete record at the end of `wikidata.jsonl`, `companies.jsonl`, `wikidata-xids.jsonl`, `steam.jsonl`, `steam-dlc-ids.jsonl` or `steam-dlc.jsonl`, says so, and fetches that item again. A bad record anywhere earlier stops the run. A Steam record written by the older `appdetails` route is fetched again by the Web API route. An interrupted DLC listing continues after the highest DLC ID already written.

## Mobile hardware references (staging only)

Phone and tablet hardware facts, manufacturer support statements and publisher device listings are read by hand from manufacturer and store pages, then loaded by `scripts/catalogue/import-mobile-references.ts` into the `mobile_*` staging tables of `src/db.ts`. Each row keeps the page URL and the day it was read. These pages are mutable and have no revision link, so a row records what a page said on that day, not a pinned source version. The rows are therefore staging observations, not catalogue facts: nothing shows them as fact until a later reviewed unit adds a refresh and re-verification rule. No page text, image or review is stored; values are short facts with units. A value a source does not state is recorded as not stated, never estimated. Conflicting statements are kept side by side and quarantined; no script picks a winner. No collector, scraper or store API is used, and none is authorised by this section.

## Device-inclusive evidence (AI-094)

`src/lib/evidenceContract.ts` defines `mgpl-dpx-evidence/1`, the record every device-inclusive unit uses for a game, store-listing, hardware or OS fact. Each record names one exact subject, one field from a closed list with a fixed unit, the country it applies to, the source page and the day it was read. A value a source does not state is `unknown`, with a reason, never zero, `false` or "unsupported". A missing listing in a list the source does not call complete is `not_listed`, not "no". Estimates are not accepted; performance needs a measured method. Titles never identify anything. Mobile hardware facts stay in the staging contract above.

`src/lib/sourceAccess.ts` records, per source and field, how it may be collected, whether it may be stored and whether it may be shown. Anything undecided is withheld. No host is listed there, and no automated route is approved:

- Apple Search API: a candidate only. Apple allows about 20 calls a minute, for promoting store content, and asks for content to be removed on request. Use, hosts and the five-app pilot wait for the Principal Operator's decisions.
- Google Play: no public catalogue API exists for other developers' apps. Listings are read by hand.
- Store, publisher and manufacturer pages: short facts with a link per fact may be stored; showing them waits for a decision. The kind of source a record names is the recording person's statement, reviewed when it is stored; it can never make a fact more publishable than the evidence supports.
- Wikidata: CC0, linked per fact as above. Showing Wikidata facts waits until a citation can be checked against Wikidata's own site; until then they are withheld like the rest.

A fact expires for current use after 7 days for store listings, 30 days for requirements and compatibility, and 90 days for hardware, support and labels. These periods are MGPL's choice; no source sets one. An expired, conflicting or withdrawn fact is kept as history and never deleted by expiry. `src/utils/guardedFetch.ts` is the request path for future device-inclusive adapters, and has no host of its own. A host list given to it is an allowlist entry that only the Principal Operator places. It allows exact host and path only, follows no redirects, refuses every address that is not globally reachable according to IANA's special-purpose registries (plus a few deliberate extras) inside the connection and checks that it is connected to an address it validated, verifies TLS explicitly, bounds size, time and retries, remembers how long a source asked it to wait and does not send again before then — a wait longer than any calendar date stops requests to that source until a person clears it — and stops after access is denied, after an unexpected destination, or after three calls in a row end in a temporary failure. Requests to Apple need the operator's approval as a new integration; they are not billable calls under the spending ledger.

## Shared identities and admitted evidence (AI-095)

`src/db.ts` holds the shared identity tables for device-inclusive work, all named `dpx_*`: game works (a Wikidata item `wd:Q…` or a curated `mgpl:` slug where no item exists), reviewed links saying an `mgpl:` work is a Wikidata item, exact editions (`<work>/<slug>`), store products (store and app ID) linked to one edition, and non-phone hardware families and references. A reference with a published model code is identified by that code; one without a code is identified by its market and configuration, and stays unresolved until a reviewed correction. Two regional models are never merged, and no title, marketing name or platform label identifies anything.

The same tables keep the `mgpl-dpx-evidence/1` records described above, after admission: each record is validated by `src/lib/evidenceContract.ts`, and its subject must already exist — including any phone or tablet key, which must exist in the mobile staging tables, whose rows and keys this never changes. Each record keeps the classification and publication state it had when admitted; what may be shown is always recomputed from the current source register.

Rows arrive only through `scripts/catalogue/import-dpx-identities.ts`, an offline command that never opens the application database by default and refuses production. Each identity cites the page it was read from and the day; there is no collector. A dry run lists, per source class, the hosts cited, with the digests of the input and of the planned rows. The person applying the import checks that each host belongs to the class it is filed under, then runs the apply step with those two digests; if the file or the rows it would write have changed since the review, the apply refuses and writes nothing. The same file applied twice changes nothing. Rows are never edited or deleted by the import; corrections are a later reviewed workflow. `scripts/rollback-dpx-identity-tables.sql` removes these tables without touching any other table.
