# AI-043: preprod shuts down cleanly on SIGTERM (#90)

**Correction first: the count is 15, not 16.** Earlier reports, the resume prompt's pass condition and the first commit message said the app opens 16 SQLite handles. That number came from reading the source, and I miscounted: I wrote "15 route handles plus `db.ts`" when it was 14 plus `db.ts`. A later grep appeared to confirm 16 because it also matched `export function openDatabase` in `src/scripts/schema-tools/schemaTooling.ts`. Preprod logged `closed 15`, and wrapping the `better-sqlite3` constructor at load (§2) settles it: **15 handles are opened at load, and all 15 are registered and closed.** No handle escapes the registry. The miscount was only discovered because the pass condition compared the log against a constant. Shutdown therefore no longer does that: it asserts the invariant `closed === registered` (commit 83285da). The number 15 is today's count at load. The invariant is what is being asserted.

## 0. P1 from Codex review: the drain was not a bound under lock contention

**Finding.** The 5 s drain deadline is a `setTimeout` on the event loop that also runs better-sqlite3's synchronous calls. A write that waits on another connection's lock blocks the loop, and the deadline with it, for up to that handle's busy timeout: 10 s on `db.ts`'s handle, and 5 s on every route handle, which get better-sqlite3's default (measured: `pragma busy_timeout` on a fresh handle returns `5000`). A contended write during the drain pushed exit past Docker's 10 s grace period, giving exit 137 with the handles open. That is the original defect again, under load. Codex measured a 50 ms deadline firing at 256 ms. §0.3 and §0.4 reproduce it with real SQLite, and §0.5 reproduces it on preprod with Litestream running.

**#101 was merged into `develop` (`2149fe5`, 2026-09-24T18:47:57Z) before this fix landed.** `develop` therefore has the unbounded drain until the follow-up PR merges. `main` does not have #101.

**Fix.** It was written and first demonstrated as `cdaaa0e` (tree `ae0d92791678eabe0098a6f4e6a61082a603254b`) on the #101 branch. It was then rebased onto `develop` as `5cb1f02` (tree `42e7cdb01b4e1160f5d6040d41d32eb9bf593af2`). The two commits differ only in `DOCS/BDR_DRILL_LOG.md`, which came in from #100. §0.3 and §0.4 ran `cdaaa0e`; §0.5 ran `5cb1f02`. The fix has two parts, and §0.4 shows that neither part is enough alone.

1. **Shorter waits during shutdown.** Before the drain starts, the handler sets `busy_timeout = 250` on every open registered handle (`shortenBusyTimeouts()` in `src/lib/dbHandles.ts`). A contended call during the drain then fails with `SQLITE_BUSY` after about 250 ms. In-flight writes may fail: the register request in §0.4 got HTTP 500. That is acceptable during shutdown, and better than a hard kill with an unclean close. The first shutdown log line now reports the count, for example `SQLite busy timeout 250 ms on 15 of 15 registered handle(s), 0 failed`.
2. **`stop_grace_period: 30s`** on the app service in `docker-compose.preprod.yml` and `docker-compose.yml`. Compose v5.5.1 was checked locally to set the container's `StopTimeout` to 30 from this key.

### 0.1 What part 1 does not cover

- **A call already waiting when SIGTERM arrives.** The signal handler cannot run until that call returns, and changing the pragma cannot interrupt a wait in progress. Only the grace period covers this case (§0.4, `blocked` rows).
- **Per-request handles in `library.ts` and `sync.ts`.** These are opened in `withDb`, are not registered, and keep the 5 s default. A request in flight that opens one during the drain can delay the deadline by up to 5 s. These files were left unchanged because Codex's area 3 came back clean. The grace-period arithmetic below includes this case.
- **Synchronous retries.** `withDpmRetry` (`src/services/devicePlayability.ts`) retries a failed playability scan immediately, without yielding, with `attempts = 2`. Before the signal is handled, that is up to 2 × 5 s = 10 s on `devices.ts`'s handle, the same as one `db.ts` wait. During the drain, it is 2 × 250 ms. I did not audit every route for code that catches `SQLITE_BUSY` and continues synchronously. Such code would add one wait for each contended call it makes.

### 0.2 Grace-period arithmetic

| Term                                                                           | Worst case                       |
| ------------------------------------------------------------------------------ | -------------------------------- |
| A call already waiting when the signal lands (`db.ts` busy timeout)            | 10 s                             |
| Drain                                                                          | 5 s                              |
| Deadline lateness from a `withDb` per-request handle (unregistered)            | 5 s (registered handles: 0.25 s) |
| Close: 15 × `sqlite3_close`, WAL checkpoint on close is passive (no busy wait) | not a lock wait; I/O-bound       |
| **Total before close**                                                         | **20 s**                         |

This leaves 10 s of the 30 s for the closes and process exit. With 10 s, Docker's default, the first two rows alone already use the whole budget. The measured worst case in §0.4 was 14.3 s.

### 0.4 `docker stop` under contention: local Docker

These runs used local Docker Desktop (Compose v5.5.1), because SSH to preprod was refused at first. §0.5 has the preprod runs, done once SSH was allowed. These are real `docker stop` runs of the full app image with real contention. There is no Litestream or Caddy, so no other long-lived connection to the database: an easier case than preprod.

Setup for each run:

- A fresh named volume.
- The app container: `NODE_ENV=production`, `DISABLE_CRON=true`, a throwaway `JWT_SECRET`, and `--stop-timeout` set to the grace period under test.
- A second container from the same image, on the same volume, holding `BEGIN IMMEDIATE` on the app's database. This is the second connection holding the write lock.

### 0.6 Two corrections from the Codex review

- **Area 2: registry completeness.** Codex found no unregistered long-lived handle **by its own reading of the code**, and said explicitly that the startup test alone does not establish that. `test/unit/dbHandleRegistry.test.ts` proves that every handle opened **at load** is registered. It does not prove that no handle is opened later: lazily, in a background job, or in an error path. That claim rests on Codex's analysis, not on a test.
- **Area 5: close with a backup running.** The PR body said an unfinished `/backup` could make the close fail. That overstated it. In the installed better-sqlite3 (13.0.3), `Database::CloseHandles` calls `Backup::CloseHandles` on every live backup (`sqlite3_backup_finish`, then removing the destination file if the backup created it) before `sqlite3_close` (`src/objects/database.cpp:36-45`, `backup.cpp:21-29`). An unfinished backup does not by itself make `close()` throw. `close()` throws only if the connection is busy or has an open iterator (`REQUIRE_DATABASE_NOT_BUSY`, `REQUIRE_DATABASE_NO_ITERATORS`). What the interrupted `/backup` request then returns to its client was not tested.

## 1. Why SIGTERM was ignored, confirmed on the host

Node is PID 1 in the container, because the Dockerfile uses exec form `CMD ["node", "dist/index.js"]` and compose does not override it. Node installs its own SIGTERM handler, which resets the signal to its default action and re-raises it. The kernel never applies a default action to a PID namespace's init process, so the re-raised signal is dropped. With no application-level handler, SIGTERM did nothing and Docker killed the process at its 10 s timeout.
